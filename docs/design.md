# CAROM — 설계 문서

세로 9:16 모바일 2D 당구 퍼즐. 한 손 조작. Verse8 배포.

> 이 문서는 **현재 구현**을 기술한다. 이전 콘셉트(충격파 하이스코어, 무한 생존형 예지)는
> 전부 폐기됐고 여기 남아 있지 않다.

---

## 1. 코어

닫힌 아레나 안에서 큐볼과 공들이 벽과 서로에게 튕기며 계속 움직인다. **아무것도 멈추지 않는다.**

**조작은 하나** — 화면을 누르고 **반대로 당겼다 떼면** 그 방향으로 발사한다(새총).
- 누르는 동안 물리가 0.18배로 느려져 각을 읽을 수 있다
- **제한 시간은 실제 속도로 흐른다.** 오래 조준하면 그만큼 손해다
- 손가락이 항상 발사 방향 반대편에 있어 조준선을 가리지 않는다
- 16px 이내로 당기면 발사되지 않는다(오터치 취소). 이때 조준선도 사라져 취소 상태가 드러난다

**조준선이 이 게임의 얼굴이다.** 상태를 복제해 실제와 똑같은 물리·규칙으로 빨리 감아 그린다.
근사가 아니라 정확한 미래다. 벽 튕김, 공 튕김, 타깃 파괴, 폭발 연쇄, 포탈 통과까지 전부 반영된다.

- **색이 곧 판정** — 금색이면 타깃을 부수고, 빨강이면 실패하고, 파랑이면 아무 일도 없다
- **2선분까지만 그린다** — 만파워는 3초에 대여섯 번 튕겨서 화면이 선으로 덮인다
- **그리는 것만 자르고 계산은 끝까지 한다** — 큐볼이 튕긴 뒤에 결과가 나오는 샷(bankShot)을 확인할 수 없게 되기 때문
- **경로 끝에서 실패하면 반드시 알린다** — 첫 충돌만 보면 "타깃 맞히고 튕겨서 죽는" 샷이 안전해 보인다

## 2. 화면에 있는 것

| 보이는 것 | 역할 | 규칙 |
|---|---|---|
| 시안 발광 구슬 | **큐볼** | 절대 안 멈춤. 잔상·이중 링으로 강조 |
| 금색 링 두른 소행성 | **타깃** | 부숴야 할 것 |
| 빨간 각진 금속 | **위험물** | 닿으면 즉시 실패. 못 부숨 |
| 회색 파편 | **중립구** | 각을 만드는 공. 큐볼에 맞으면 1.6초간 충전되고, 그 상태로 타깃을 치면 부숨 |
| 주황 캐니스터 | **폭발통** | 맞히면 반경 135 안 타깃 일괄 파괴, 다른 폭발통도 연쇄 |
| 무채색 기둥 | **벽** | 안 움직이고 안 부서짐. 당구대의 모양을 바꿈 |
| 보라 링 쌍 | **포탈** | 큐볼만 통과. 양방향, 0.35초 재진입 금지 |

**발광을 주면 공으로 보이고, 공으로 보이면 부술 수 있다고 착각한다.** 그래서 벽만 무채색이다.

---

## 3. 클리어 / 실패

**클리어 = 타깃 전부 파괴.** 실패는 둘뿐 — **위험물 접촉**, **시간 초과**.

**샷 횟수 제한은 없다.** 시간이 유일한 압박이다. 별점도 없다.

시작 1.4초는 무적이다. 오브젝트가 20개를 넘으면 배치가 아무리 조심스러워도 공이 흘러와 닿는데,
첫 샷도 못 쏘고 지는 것은 플레이어의 실수가 아니다.

---

## 4. 스테이지 — 번호 하나에서 전부 유도

손으로 만든 레벨 데이터가 없다. 같은 번호는 항상 같은 판이라 재도전이 성립한다.

세 축이 **서로 다른 주기로** 돌아 조합이 곱해진다. 최소공배수 **126**.

**조건 (6주기)** — 기본이 절반
| 조건 | 규칙 |
|---|---|
| `destroyAll` | 전부 파괴 |
| `noNeutral` | 중립구에 닿으면 실패. 각을 만들던 공이 지뢰가 된다 |
| `bankShot` | 큐볼로 직접 못 부숨. 중립구나 폭발통을 거쳐야 한다 |
| `inOrder` | 번호 순서대로만. 순서가 아니면 **실패가 아니라 안 부서진다** |

**테마 (9주기)** — `open` `pillars` `corridor` `barrier` `scatter` `cross` `ring` `funnel` `columns`

**모디파이어 (7주기)** — 숫자 하나씩만 바꾼다
`swift`(속도 ×1.35) `shortLine`(조준선 1선분) `tightTime`(시간 ×0.62) `noSlow`(조준해도 안 느려짐)

**도입 시점을 어긋나게 둔다** — 위험물 3, 폭발통 5, 조건 7, 포탈 8, 모디파이어 10스테이지부터.
한 번에 다 나오면 배우지 못한다.

### 규칙끼리 모순되는 조합은 생성 단계에서 막는다

- `inOrder`에는 폭발통 0 — 한 방에 여러 개를 부수면 순서를 지킬 방법이 없다
- `inOrder`는 타깃 5개 상한 — 매 샷이 특정 한 개를 노려야 해서 곱으로 어려워진다
- `noNeutral`은 중립구·위험물 절반 — 둘 다 치명적이면 지나갈 틈이 없다
- `bankShot`은 중립구 최소 3 — 거쳐 갈 것이 없으면 풀 수 없다
- `barrier` 테마는 조건을 `destroyAll`로 고정하고 포탈을 강제 1개 — 넘어가는 것 자체가 과제다

### barrier — 포탈 전용 테마

벽이 아레나를 **틈 없이** 가른다. 타깃은 전부 위, 플레이어는 아래. 넘어갈 방법은 포탈뿐이다.
틈을 하나라도 남기면 포탈이 지름길이 아니라 선택지가 되고, 이 테마가 존재할 이유가 사라진다.

### 측정값

- 서로 다른 설계 **108가지**, 처음 겹치는 지점 **44스테이지**
- 봇 클리어율 **29/30**, **무입력 클리어 0/20** (수동적 최적해 없음)

## 5. 기술 구조

**스택** — Vite + React + TypeScript, Canvas 2D 직접 렌더. `@agent8/gameserver`. 루트 `server.js`.

게임 프레임워크는 쓰지 않는다. 원 20개짜리 물리에 프레임워크를 얹으면 의존성 리스크만 늘고 얻는 게 없다.

```
├── server.js                  # Agent8 서버 함수 (루트, export 금지)
├── public/assets/             # docs/asset-prompts.md 참고
└── src/
    ├── game/
    │   ├── config.ts          # 튜닝 숫자 전부 여기 한 곳
    │   ├── types.ts
    │   ├── rng.ts             # 시드 기반 난수
    │   ├── engine.ts          # 시뮬레이션 (결정적)
    │   ├── physics.ts         # 원-원 충돌, 벽, 포탈
    │   ├── rules.ts           # 파괴·폭발·연쇄 규칙의 유일한 구현
    │   ├── foresight.ts       # 조준선
    │   ├── shot.ts            # 당김 → 임펄스 변환
    │   ├── stage.ts           # 번호 → 스테이지
    │   ├── assets.ts          # 알파 바운딩박스 기준 스프라이트 정규화
    │   └── renderer.ts        # Canvas 2D (읽기 전용)
    ├── audio/                 # 배경음·효과음 (파일 없이 합성)
    ├── hooks/
    │   ├── useGameLoop.ts     # rAF + 고정 timestep
    │   ├── useWallet.ts       # 서버 지갑 · 오프라인 폴백
    │   ├── useRanking.ts      # 랭킹 자동 등록
    │   └── useAdReward.ts     # 광고 보상 1회 수령
    ├── net/
    │   ├── leaderboard.ts     # 서버 호출
    │   └── ads.ts             # Verse8 Ads 래퍼
    ├── i18n/                  # 한국어 · English · 简体 · 繁體
    ├── shop.ts                # 코인 상점 (가격은 server.js가 정본)
    ├── progress.ts            # 진행 저장 (오프라인 전용)
    ├── tutorial.ts            # 튜토리얼 열람 여부 (로컬)
    ├── features.ts            # 미구현 기능 스위치
    └── ui/                    # Title / Game / Leaderboard / Shop / Settings / Tutorial
```

### 지켜야 하는 경계 세 개

**1. 시뮬레이션은 결정적이다.** 같은 시드 + 같은 입력열 → 같은 결과.
조준선이 상태를 복제해 빨리 감는 방식이라, 비결정성이 섞이는 순간 보여준 궤적과 실제가 갈라진다.
난수는 시드 기반(`rng.ts`)만 쓴다. `Math.random()`은 새 판을 시작할 때만 쓴다.

**2. 규칙은 `rules.ts` 하나뿐이다.** 엔진과 조준선이 같은 함수를 호출한다.
규칙이 두 벌이면 조준선이 거짓말한다 — 실제로 그 사고를 냈다(금색 타깃이 안 부서지던 버그).

**3. `renderer.ts`는 상태를 읽고 그리기만 한다.** 그래서 아트 교체가 물리를 건드릴 수 없다.

### 접촉 판정

충돌 해소가 두 원을 정확히 맞닿는 거리로 밀어내므로, 그 뒤에 겹침을 재면 경계값에서
부동소수점에 따라 참/거짓이 갈린다. **물리가 실제로 해소한 충돌을 그 순간 기록**해서
게임 판정이 그 목록만 보게 한다. "얼마나 겹쳐야 닿은 것인가"를 추측하지 않는다.

### 루프

`rAF` → 누적 시간을 **고정 timestep 1/60**으로 쪼개 `step` 반복 → `draw`.
가변 timestep을 쓰면 프레임 드랍마다 결과가 달라진다.

조준선은 조준 중일 때만 매 프레임 계산한다. 실측 비용은 물체 25개 기준 데스크톱 0.10ms,
모바일 환산 약 0.5ms — 프레임 예산의 3%라 캐싱하지 않는다.

## 6. 서버 / 리더보드

`submitProgress(stage, nickname)` / `getTopRankings()` / `getMyRank()` / `redeemAdReward(...)`
`getWallet()` / `recordClear(...)` / `spendCoins(...)` / `buySkin(...)` / `equipSkin(...)` / `migrateLocal(...)` / `$onItemPurchased(...)`

**등록은 자동이다.** 스테이지를 깰 때마다 바로 올라간다(`useRanking.submit`).
등록 버튼을 따로 두면 안 누른 사람의 기록이 통째로 빠져 랭킹이 실제 분포를 못 보여준다.
닉네임이 없으면 계정에서 `PLAYER-XXXX`를 만들어 쓰고, 랭킹 창에서 바꿀 수 있다.
이름만 바꿀 때는 `updatedAt`을 건드리지 않는다 — 동점 정렬이 "먼저 도달한 순"이라
개명이 순위를 떨어뜨리면 안 된다.

**순위 기준은 최고 도달 스테이지 하나뿐이다.** 점수가 없고 진행도만 있으므로 순위의 의미도
그것뿐이다. 같은 스테이지면 먼저 도달한 쪽이 위. 계정당 기록 하나만 유지한다 —
여러 개 쌓이면 상위 20위가 한 사람으로 채워진다.

**시간은 순위에 쓰지 않는다.** 진행 시간은 클리어한 판만 누적되고 실패한 시도는 세지 않는다.
그래서 한 번에 깬 사람과 50번 실패하고 깬 사람이 같은 값으로 찍힌다 —
그런 값으로는 실력을 가릴 수 없어 동점자 기준이 될 수 없다.

**알려진 한계** — 클라이언트가 도달 스테이지를 부풀려 보내는 것은 막지 못한다.
완전히 막으려면 서버가 시뮬레이션을 재현해야 하는데 범위 밖이다.

배포: `npx -y @agent8/deploy`

## 7. 광고

**보상형 2개만. 전면 광고는 쓰지 않는다.**

| placementId | 자리 | 보상 |
|---|---|---|
| carom-revive | 실패 화면 | 시간 +12초 |
| carom-double-coins | 클리어 화면 | 그 판에서 번 코인만큼 한 번 더 |

### 지키는 규칙

1. **사용자 제스처에서만 호출한다.** 자동 표시는 정책 위반이다. onClick 밖에서 부르는 코드 경로를 아예 만들지 않는다.
2. **status가 rewarded일 때만 보상.** dismissed·failed는 아무 일도 일어나지 않는다.
3. **환경이 광고를 지원하지 않으면 버튼을 숨긴다.** 눌러도 매번 실패하는 버튼이 남아 있는 것이 가장 나쁘다.
4. **재화는 서버가 지급한다.** 지급량은 서버 표가 정하고, (계정, requestId)를 기록해 같은 시청의 재사용을 막는다. 클라이언트가 보낸 reward는 UX 힌트일 뿐이다.
5. **판단 불가는 거절이 아니다.** 검증자가 "안 봤다"고 명시할 때만 거절한다. 대답을 못 얻으면 지급한다 — 플랫폼이 침묵한다고 광고를 본 사람을 빈손으로 보낼 수는 없다.
6. **부활은 서버를 안 거친다.** 그 판을 이어할 뿐 재화가 아니다.

### 서버 검증이 안 되는 이유

Verse8은 SSV 결과를 **게임 서버에 열어주지 않는다.**

| 경로 | 게임 서버가 부르면 |
|---|---|
| `POST /ads/verify` | `401 unauthorized` |
| `GET /ads/status` | `202` pending에 머묾 |

`PROTOCOL.md` §10의 인증 표는 셸(shell)용 `/ads/result`만 다루고, 게임 서버용 자격 증명은 문서에 없다.
같은 플랫폼의 다른 게임도 서버 검증 없이 클라이언트 결과로 지급한다
(@verse8/ads 래퍼 주석: *"requestId is reserved for future server-side verification"*).

**이걸 모르고 검증 실패를 거절로 처리했더니, 광고를 끝까지 본 사람이 매번
"보상을 확인하지 못했습니다"를 봤다.** 지금은 명시적 부정일 때만 거절한다.

### 남은 구멍

코인은 서버가 지급한다(아래 §8). 남은 구멍은 둘이고, 둘 다 서버가 못 막는다:

1. **"그 판에서 정말 그만큼 벌었는가"** — 서버가 시뮬레이션을 재현하지 않는 한 확인 불가.
   스테이지당 상한(`MAX_COINS_PER_STAGE = 200`)으로 무제한 발급만 잘라낸다.
2. **"그 requestId가 진짜 시청인가"** — 위 이유로 검증 경로가 없다.
   조작한 requestId를 새로 만들어 부르는 것은 못 막는다.
   막아주는 것은 (계정, requestId) 기록과 스테이지당 상한뿐이다.

플랫폼이 게임 서버용 검증 경로를 열면 2번은 닫힌다. 그때 hard 거절로 바꾸면 된다.

## 8. 지갑 · VXShop

### 코인 경제 — 가격은 측정에서 나온다

`npm run sim`이 봇으로 30스테이지를 깨면서 코인 수급을 같이 잰다. 가격을 감으로 정하지 않는다.

코인은 두 갈래로 들어온다:

* **클리어 보상** `10 + 타깃수 × 2` — 끝냈다는 것에 대한 보상
* **연쇄·폭발 보너스** — 잘했다는 것에 대한 보상

처음에는 연쇄·폭발만 있었다. 그래서 한 번에 하나씩 깔끔하게 부수면 **깨고도 0코인**이었고
(측정: 1·5·19스테이지가 0), 그때 "코인 2배" 광고 버튼이 2배로 만들 것이 없어 잠겼다.
깬 사람에게 아무것도 안 주는 것보다 그쪽이 더 나빴다.

| | 값 |
|---|---|
| 클리어당 코인 | 평균 42.1 · 중앙값 44 · **최소 16** · 최대 64 |
| 누적 | 3스테이지 66 · 8스테이지 212 · 20스테이지 744 · 30스테이지 1222 |

코인은 **클리어할 때만** 들어온다. 실패한 시도는 0이다.

클리어 보상은 `engine.step`에서만 준다. `resolveRules`는 조준선(foresight)도 함께 쓰는 코드라
거기에 넣으면 아직 쏘지도 않은 예측이 코인을 세게 된다.

**이어하기 = `60 + 20 × ⌊(stage-1)/10⌋`** (1~10스테이지 60, 11~20 80, …)

지키려는 것은 금액이 아니라 **중앙값 수입의 1.5판치**라는 비율이다.
코인은 클리어할 때만 들어오므로, 실패가 잦은 초반에 낼 수 없는 값을 매기면
버튼이 아예 안 뜬다 — **못 사는 가격은 가격이 아니다.** 60이면 3스테이지쯤부터 선택지가 생긴다.
10스테이지마다 올리는 이유는 후반 수입이 오르기 때문이다.

남용은 가격이 아니라 **스테이지당 1회 제한**(`hud.canRevive`, 광고 부활과 공유)이 막는다.

**스킨 = PULSE 200 · JADE 700** (`src/shop.ts`와 `server.js`의 `SKIN_PRICES`가 같아야 한다.
차감은 서버 표가 하므로 어긋나면 화면 값과 실제 값이 달라진다.)

JADE는 원래 EMBER(주황)였는데 폭발통과 똑같이 생겨서 색을 바꿨다. **`id`는 `ember`로 둔다** —
색이 바뀌었다고 `id`를 바꾸면 서버 지갑의 `owned` 배열과 `SKIN_PRICES` 키가 어긋나
이미 산 사람이 스킨을 잃는다. 보이는 이름만 바꾼다.

`npm run sim`의 "가격별 도달 스테이지":

| 가격 | 100 | 200 | 300 | 500 | 700 |
|---|---|---|---|---|---|
| 스테이지 | 5 | 8 | 10 | 15 | 20 |

200이면 첫 세션 안에 하나 산다. 700은 20스테이지대의 목표로 남는다.
이어하기까지 쓰면 실제로는 각각 2~3스테이지 뒤로 밀린다.

금액 자체는 예전(80/300)보다 크지만 클리어 보상으로 수입이 2.2배가 됐으므로
**도달 스테이지로 보면 같거나 앞당겨졌다.** 가격은 금액이 아니라 도달 시점으로 정한다.

### 코인은 서버 소유다

실제 결제가 얽힌 이상 클라이언트가 재화를 소유하는 구조는 둘 수 없다 — localStorage는 고치면 그만이다.
`$global.getMyState/updateMyState`에 지갑 하나를 둔다:

```
{ coins, reached, owned[], equipped, coinBoost, noAds, purchases[], migrated }
```

* 스킨은 **코인으로만** 산다. 가격은 **서버 표**(`SKIN_PRICES`)가 정한다 —
  클라이언트가 보낸 가격은 받지 않는다.
* 광고 코인 2배도 서버가 직접 넣고 지갑을 돌려준다. 클라이언트에게 "이만큼 넣어라"라고 시키지 않는다.
* 서버에 연결 안 되면 로컬로 돌아간다 — 서버가 없다고 게임이 멈추면 안 된다.
  그때 번 것은 그 기기에만 남고, 처음 연결될 때 `migrateLocal`로 **한 번만** 올라간다.

### VX 상품 — 광고 제거 하나뿐

| Product ID | 이름 | 가격 | 주는 것 |
|---|---|---|---|
| `carom-no-ads` | NO ADS | 100 VX | 광고 제거 + 모든 클리어 코인 **2배** (영구) |

지급은 오직 `$onItemPurchased`만 한다. 클라이언트를 거치지 않는 경로라서 그것만 실제 결제다.
같은 `purchaseId`가 두 번 와도 한 번만 반영한다.

**코인 2배는 덤이 아니다.** "코인 2배" 보상형 광고가 사라지는데 그 이득까지 같이 사라지면
돈을 낸 사람이 안 낸 사람보다 코인을 덜 벌게 된다. 없앤 것을 대신 채워주는 것이다.

| | 사기 전 | 산 뒤 |
|---|---|---|
| 클리어 코인 | 기본 | ×2 (적립 시점에 서버가 곱함) |
| "광고 보고 코인 2배" 버튼 | 있음 | 사라짐 — 이미 2배라 또 주면 4배 |
| "광고 보고 시간 +12초" 버튼 | 광고 시청 | 광고 없이 즉시 (스테이지당 1회는 그대로) |

부활 버튼을 없애지 않는 이유: 광고를 없앤 대가로 기능까지 잃으면 결제한 쪽이 나빠진다.
버튼은 남기고 광고만 걷어낸다.

서버도 같은 것을 막는다 — `noAds`인 계정이 `redeemAdReward`로 코인 2배를 또 요청하면
`already_doubled`로 거절한다. 클라이언트가 버튼을 숨기는 것은 UI일 뿐이다.

**스킨·코인은 VX로 팔지 않는다.** 코인을 모을 이유가 남아 있어야 "코인 2배"가 값어치를 갖고,
그래야 이 상품 하나가 팔린다. 스킨까지 VX로 팔면 코인 경제를 스스로 망가뜨린다.

**순위에 영향을 주는 것도 팔지 않는다.** 리더보드가 도달 스테이지라
진행 속도를 파는 순간 순위는 결제 순위가 된다.

썸네일(512×512)은 `npm run vx-products`로 만든다 → `docs/store-assets/vxshop/`.
게임에 실제로 있는 아이콘만 쓴다 — 상품 이미지와 받는 것이 다르면 그건 거짓말이다.

## 9. 사운드 · 튜토리얼

### 소리는 파일이 아니라 합성이다

루프 파일을 쓰면 몇 MB가 붙고, 짧게 자르면 반복이 금방 들킨다. 스테이지를 번호 하나에서
만들어내는 게임에 고정 길이 오디오를 붙이는 것도 어울리지 않는다. 전부 Web Audio로 그 자리에서 만든다.

| 파일 | 역할 |
|---|---|
| `audio/engine.ts` | 합성 노드와 출력 |
| `audio/music.ts` | 배경음 |
| `audio/sfx.ts` | 효과음 |
| `audio/index.ts` | 공개 API |

**당구 게임이라 접촉음이 제일 중요하다.** 공이 닿았는데 소리가 없으면 맞은 건지 스친 건지 알 수 없다.
음량은 설정에서 따로 조절한다.

### 튜토리얼은 첫 판에만

`tutorial.ts`가 열람 여부를 **로컬에만** 저장한다. 재화가 아니라 화면 설정이고,
저장이 날아가서 한 번 더 보는 것이 못 보는 것보다 낫다.

내용은 세 가지 — 당겼다 떼면 발사 / 선은 결과를 미리 보여준다 / 금색 물체를 전부 부수면 클리어.
여기에 조준선 색 범례(빗나감 · 부순다 · 폭발 연쇄 · 여기서 실패)를 같이 띄운다.
**색이 곧 판정인데 그 색을 안 알려주면 조준선이 그냥 장식으로 보인다.**

### 아직 없는 것

클리어 / 실패 연출. 현재는 텍스트 오버레이만 띄운다.

```bash
npm run sim                        # 봇이 30스테이지를 실제로 깨보는 검증
npx tsx scripts/idle-check.ts      # 무입력으로 클리어되는지 (수동적 최적해 검사)
npx tsx scripts/cycle-check.ts     # 설계 종류·반복 지점
npx tsx scripts/stage-table.ts     # 스테이지별 구성표
npx tsx scripts/perf-foresight.ts  # 조준선 계산 비용
```
